# DESIGN.md — 제품 디자인 계약

> **이 문서는 "무엇을 만드는가"가 아니라 "어떤 인상을 주는가"를 정의한다.**
> SPEC.md가 기능의 계약이라면 DESIGN.md는 **성격의 계약**이다.
> UI 구현 중 색·간격·모서리·폰트를 정할 때 근거로 삼는 문서이며, 여기 없는 값은 임의로 정하지 않는다.
> (스펙 공백 시 임의 구현 금지 규칙의 디자인 버전)
>
> ⚠️ **이 문서가 틀리면 결과물은 "일관되게 틀린" 디자인이 된다.** 값보다 이 문서의 검토에 시간을 쓸 것.

**적용 대상**: `projectScope.hasFrontend=true`인 프로젝트 (필수)

**범위 구분**: 여기에는 **보이는 것**의 결정만 적는다. 프레임워크·상태관리·빌드 도구 같은
구조적 결정은 여기가 아니라 `docs/adr/`에 ADR로 기록한다 (번호 체계를 새로 만들지 않는다).

## 출처 표기 규칙

`doc-planning-common.md`의 **Provenance 마커 프로토콜**을 그대로 따른다.
각 핵심 섹션 헤딩 직후 첫 비공백 줄에 마커 1개:

```markdown
<!-- provenance: user-fact -->
<!-- provenance: repo-fact:src/styles/tokens.css -->
<!-- provenance: assumption: 8pt grid는 관례이고 되돌리기 쉬움 -->
<!-- provenance: blocker -->
```

**제품 성격(1절)과 브랜드 정체성(2절)은 `assumption` 금지 — `user-fact` 또는 `blocker`만 허용.**
추측한 성격은 전 화면에 일관되게 전파되어 되돌리기가 가장 비싼 결정이기 때문이다.
모르면 `blocker`로 두고 `[NEEDS-CLARIFICATION: <질문>]`으로 전환해 batch-ask에서 해소한다.

토큰 스케일(4절)처럼 국소적·가역적인 결정은 근거를 붙인 `assumption`이 허용된다.

## 5. 화면 상태 계약

<!-- provenance: user-fact -->

**컴포넌트는 default 하나가 아니라 상태의 집합이다.** SPEC의 `UI States` 표와 1:1로 대응한다.

| 상태 | 표현 규칙 |
|------|-----------|
| 빈 상태 | 안내 문구 + 다음 행동 CTA. 빈 박스만 두지 않는다 |
| 로딩 | 스켈레톤(레이아웃 유지) 또는 스피너. 레이아웃 점프 금지 |
| 에러 | 원인 + 복구 행동. 필드 에러는 해당 필드 하단 |
| 유효성 | blur 시점 검증. 제출 시점만 검증하지 않는다 |
| disabled | opacity만으로 표현하지 않는다 (+ `cursor: not-allowed`) |
| focus | **반드시** 시각 변화가 있어야 한다 (WCAG 2.4.7) |

## 6. 접근성 기준선

<!-- provenance: assumption: WCAG 2.1 AA는 업계 표준 기본값 -->

- 대비: 본문 4.5:1, 큰 텍스트 3:1
- 터치 타겟: 44×44px 이상
- 키보드만으로 모든 기능 도달 가능
- 색상 단독으로 정보를 전달하지 않음

## 7. 한국어 UI (해당 시)

<!-- provenance: assumption: 한국어 UI 프로젝트의 공통 실패 지점 -->

- 폰트 스택에 한국어 폰트를 **명시**한다 (`Inter, serif`류 스택은 한글만 명조로 렌더된다)
- 긴 문단은 `word-break: keep-all`
- 자간은 -2% 미만으로 줄이지 않는다
